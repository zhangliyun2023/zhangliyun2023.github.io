Transferable Practice

可沉淀的方法论

在一个桌面 Agent 产品和一条文档自动生成链路上做实现与验收， 真正能带走的不是代码，是一批可以照抄到别的项目的判据。 下面每一条都写成三层：规则（能直接执行）、为什么（哪次事故换来的）、怎么验（一条能跑的命令或一个能失败的断言）。

以下为个人在实践中沉淀的工程笔记：已隐去源码、生产配置与内部链接，涉及的产品一律表述为「某桌面 Agent 产品」「某文档生成链路」。 文中保留的数字均为实测记录值，未做外推；来源另有出处的条目已在该条内注明。

01

撤回修复不转红，就不算验过

Rule

「验过了」必须同时满足两条：修复后绿，且证据是用户看得见的东西（DOM 文案 / aria-* / data-*，不是内部状态）； 把修复撤回后必须红，且红的内容与用户症状同形——用户说「显示了两张」，红的就该是 length 1 but got 2。 只满足第一条只能叫「我改完了」。

Why

绿只证明当前世界是好的，不证明这条用例押在了缺陷上。一条在「没有修复的世界」里也绿的测试，等于没有测到东西。 反过来，一个修复有多处改动时，只撤其中一处却没转红，说明撤错了地方，不是探针有效。 来源说明：「红-绿撤回环」本身是既有公开实践（如 verification-before-completion 一类公开 skill 的 write → pass → revert → must fail → restore → pass）； 本条的自有增量是两点——红的内容必须与用户症状同形，以及主进程改动必须重启实例，这两点有事故背书。

Check
git checkout HEAD -- <显式路径> 撤回 → 主进程改动必须重启实例（只有渲染层能靠 HMR，不重启就退代码，探针读到的仍是修复版）→ 重跑同一条用例。 撤回前后各跑一次 git diff --stat，确认只有自己那几行在动。绝不用 git stash，也不用「整份 cp 快照再还原」。
02

断言必须跨过至少一条进程或持久化边界

Rule

同一个事实要在三处同时读：界面（真实 DOM 文案与 aria-* / data-*）+ IPC（在页面里真调一次 window.<api>.<域>.<方法>()） + 磁盘（node 侧独立 existsSync / readFileSync，与渲染层状态完全无关）。三处不一致就是缺陷，不取多数。

Why

乐观更新会让只看界面的断言全线假绿：界面已经变了，数据根本没落盘。 而且同一个事实（存在性、内容版本）一旦在多处各自维护，就会长出「同一个文件四个地方四种状态」，对用户表现为「删不掉 / 不刷新 / 凭空消失」。 「界面 + 进程边界 + 持久化」三处对齐是 Electron 场景下最值钱的一条，本条的实测背书全部来自该场景。 本地状态 / 进程边界 / 持久化的同构在移动端、带缓存的 Web、CLI+DB 上看起来也成立，但那是推论，未在其他形态上验证。

Check
跨层定位不要逐层推断：一次把「数据层算出的值 / 传给渲染层的值 / 界面真实显示的值 / 相关状态位」四个并排打出来， 定位完立刻删埋点并在提交前 grep 自查。另外，fs.watch({recursive:true}) 会丢事件、合事件、rename 只给一个名字， 它是加速器，stat 探针才是裁决。
03

探测到 ≠ 用上了

Rule

凡是「有主实现 + 备用实现」的链路（渲染器、编解码器、字体、driver、模型 provider）， 必须断言实际用于渲染 / 执行的是谁，并把这个实际值写进产物元数据。 只看退出码不够；产物的数量与命名同样要逐一断言。

Why

典型失效：渲染器按输入文件名命名输出（喂 <name>-variant 出 <name>-variant.png），代码去找 <name>.png， 于是每一页都「成功但找不到文件」，整本静默降级到只画得出不到三分之一形状、画不出原生图表的备用渲染器——日志一切正常，退出码 0。 而降级发生在所有检查之前，所以后面每一层视觉与功能检查都跑在残缺产物上，全部白跑。

Check
三件事都要断言：渲染器身份、产物数量、产物文件名。 另外，注入了替身的单测证明不了接线——凡新增「一个要被调用的东西」，除单测外必须再加一条接线断言（grep 产品入口确认被引用，或真机走一次那条路）。
04

端口应答不等于活着

Rule

探活判据必须是「能列出可用资源」而不是「端口通」。三种存活状态分开处理： 没起来（连不上，起一个）／孤儿空壳（端口应答但目标列表返回 0 个 target，清掉重起）／半死（接受 TCP 但永不回响应，清掉重起）。 每个探活请求必须自带超时（AbortSignal.timeout，脚本内默认 2000ms）。

Why

不设超时的 fetch 撞上「半死」实例会永远挂着，外部表现是「卡住且没有任何输出」——最难查的一类，因为它连错误都不产生。 同一条判据对 DB、HTTP 依赖、容器健康检查一样成立。

Check
阶段推进器的探活子命令直接报出当前处于哪一态。配套两条硬约束：detached 子进程的 stdio 必须是 fd 不能是 pipe （openSync + ["ignore", fd, fd] + unref + closeSync）——否则父进程一退出读端就关， 仍在跑的主进程下一次 console.log 直接 EPIPE 未捕获崩溃，表现成「一直登不上」加一地孤儿进程； 要看输出用 readFileSync 取日志尾巴，别 on("data")。 阶段日志行也别接 | tail / | head，管道会把输出憋到进程结束才吐，要留档就 > log 2>&1 再另开窗口 tail -f。
05

模块级状态会跨用例泄漏，而且报出来的错和真因毫不相干

Rule

新增模块级缓存 / 注册表时，同时导出一个 reset*ForTests()，并在用到它的每个测试文件里 beforeEach 调用。 这是新增时的强制约定，不是出问题后再补。

Why

同类问题在同一个仓库里踩了两次，说明单次修复不解决类问题。两次真实样本：一个解码缓存在重建测试文件时被丢掉了 reset， 代码页缓存跨用例泄漏，症状报成「count=0 且解码错」；另一个默认图标缓存泄漏，「解析不出默认应用」那条用例读到了前一条用例留下的 .pdf 图标。 报出来的错和真实原因毫不相干，是这类缺陷最贵的地方。

Check
「一批不相干用例同时红」时，先去 mock 工厂找缺的方法——根组件挂载时新增一个订阅、mock 里没有这个方法， 就会直接调用 undefined 抛错，让 6 个毫无关系的用例一起红。

06 — 08 作用域：默认作用域总是比你以为的大 动手前问：这条命令的作用域，是不是只有我那几行？

06

并行改同一棵树时，所有「作用于整棵树」的操作都换成显式路径

Rule

暂存 git add <显式路径>，不用 -A / .；提交 git commit <显式路径...>，不用无 pathspec 的 commit； 回退 git checkout HEAD -- <显式路径>，不用 git stash。 「整份 cp 备份再拷回」与 stash 属于同一类作用域，不因为它不是 git 命令就安全。

Why

实测代价：一次约 1 分钟的 stash 窗口吃掉了另一组 −7/+1 的灵敏度对照改动； 一次「整份 cp 还原」把另一个 agent 刚落的三处注册表生命周期改动覆盖回旧形状，文件编译不过、两个测试文件全红， 而报出来的错（registry.history is undefined）与真因完全无关。 它们都不报错，只是静默抹掉别人在那段窗口里写入的内容。

Check
一轮开始前定死分支 / 工作树，中途不切——子 agent 的写权限钉在它启动时所在的工作树， 主会话切走后它每次写入被拒且不报错退出，只是一直重试，从外面看只是「这一组特别慢」。 分组按会冲突的文件分，不按任务编号分；组内守「一次 commit = 一个能单独回滚的决定」。
07

作用域推断不出来时，正确做法是不做，而不是猜一个

Rule

绝不监听家目录或工作区根之上。给每批路径显式的根；拿不到根就不监听，退化成「未知 ⇒ 可用」的安全方向。

Why

真实样本：一个 hook 拿不到 cwd 时，用「所有路径的公共父目录」当监听根——只要有一件交付物落在下载目录或桌面， 公共父目录就上移到 /Users/<name>，即对用户家目录递归 watch。 而数据结构本来就带着每组自己的工作目录字段，注释里甚至写着「必须逐组给根，不能让 hook 去猜一个公共父目录」。 「取一批路径的公共父目录」这类推断，在文件监听、批量删除、权限授予、清理脚本里会以完全相同的方式爆炸。

Check
把「监听根从哪来」写成显式参数而不是计算结果；渲染层拿不到 os.homedir() 时（上下文隔离）， 判家目录只能靠路径形状或从主进程透一个值过来，不能默认放行。
08

收尾按临时 profile 前缀杀，不按端口、更不按应用名

Rule

起应用一律用临时 --user-data-dir=<临时目录>，并把应用自己的数据目录环境变量也指到临时处； 收尾 pkill -f "user-data-dir=<临时前缀>"。禁止按端口杀，禁止按应用名泛杀。

Why

主进程的命令行里根本没有调试端口，按端口只杀得掉启动器，留下一地孤儿；按应用名泛杀会连用户自己开着的正式实例一起干掉。 临时 profile 前缀是唯一一个「只覆盖我这一轮起的进程」的标识。

Check
每轮结束跑 down 并确认无孤儿进程；探针脚本、截图、日志只放会话临时目录，永不进仓库。

09 — 11 门禁：可复算的阈值，而不是「注意排版」 每条都是一个能被脚本算出来的数，附带它的回归用例

09

只有「出片就是错的」才配当阻断，其余一律是警告

Rule

门禁必须分级。阻断项一旦混进假阳性，人会整体无视阻断这个信号，真缺陷跟着一起被无视。 误报比漏报更伤——信号的价值由它的假阳性率决定，不由覆盖率决定。

Why

真实代价样本：把「框挨得近」也判成阻断，一批本来没问题的文档报出大量假阻断； 当流程要求阻断项清零才能继续时，人会转而整体无视阻断这个信号。 同一份文档的报警里，约八成属于「换行后仍在框内」这种应该降级为警告的形态。

Check
三层验证越靠前越便宜：结构校验（写入时，失败要一次报全并带行号，不要报一条停一次）→ 确定性门禁（不需要模型）→ 视觉复核（需要模型能读图）。 每类误报的形态和每个真缺陷的坐标都固化成内联构造的回归用例，判据一改就跑这组。 另外，视觉复核层「读不了图就整段跳过」：图像分析连续失败 2 次（5xx / 超时 / 空结果）即判定本轮拿不到视觉证据， 立刻转结构性复核并在交付说明里注明——不重试、不拆批、不换通道。
10

算得下 ≠ 排得下：度量用的字体不是渲染用的字体

Rule
可复算的几何硬约束（以 960×540 画布、24pt 安全区为例，换画布按比例折算）：
  • 不可断短串（序号 01、5–10%、单位、年份；不含空格 / CJK 且 ≤6 字符）的框宽 ≥ 实测宽度 × 1.6；
  • 任何文本框满足 y+h ≤ 画布高−安全区、x+w ≤ 画布宽−安全区，仅页脚署名类小字可进安全区，正文不行；
  • 上下相邻文本框垂直余量 ≥ 8px；
  • 装箱折行按 92% 框宽计算，给渲染器字体替换留余量，且用真实字体文件度量 + 独立贪心折行（CJK 逐字、拉丁按词 / 连字符），不能用 ceil(宽度/框宽) 粗估；
  • 正文块框高按「字数 ÷ 每行字数 × 行高」预留。
Why

1.6 是实测值：框宽 1.47× 时离线渲染器仍然会把短串折断，而所有基于字体度量的检查都会说「没问题」。 42 高 + 40 间距 这种负余量看着能用，任一侧多换一行就压上。装不下的行不会被裁掉，会溢出框外压住下面的元素。 这套落差不属于某个格式：任何「离线度量预判版面 + 交给外部渲染器出片」的链路都有同一个洞。

Check
用版式几何门禁脚本按 0.92 装箱余量、24px 安全区跑一遍， 退出码 0 = 无阻断项（可能仍有警告）、1 = 有阻断项，可直接当出片前 gate； 自动修复只处理少数几类可安全改写的形态，做文本级改写（只改 bounds 数字、只包一层 span，保留键顺序与注释），修完自动重跑自检。 修复器必须排在渲染之前——它不看渲染产物，排后面白费一整轮渲染。
11

先归一化再和声明值比较，会让检查恒真

Rule

表格高度按每行实际需要单独算再逐行相加，禁止对行高比例做归一化，缺项等分补（照抄转换器的算法）。

Why

归一化之后，算出的总高恒等于声明高度，于是「装不下」这条检查在数学上永远不可能触发——门禁绿着，而渲染出来最后一行压到下方文字上。 实测两组：声明 262 实需 307、声明 126 实需 158，旧判据只算出 172。 「检查算法自身含有恒等式」是一类通用的门禁失效，比漏写检查更隐蔽，因为它看起来是有覆盖的。

Check
门禁标定集：13 例全内联构造、只依赖标准库、不读任何外部文件。分三类—— 真缺陷必须报出（262→307、126→158、正文真叠字约 6px）、三份逐页看过的成品必须保持沉默、 四类已知误报形态必须消除（横向不相交却报重叠 / 并排等高标签垂直 gap 恒为负 / 单行 12px 距页脚净空 6px 被误判 / 30px 字在 48px 框内居中被误判）。 判据与它的回归集必须放在一起，改判据先跑这组。

12 — 13 全绿之后 单测绿 + 类型检查绿 + 逐项真机验证，三者齐备之后剩下的那部分

12

缺陷不在实现里，在组合里

Rule

「每条修复各自单测绿 + 各自真机验过 = 这个版本可以发」是错觉。 合并发布前必须做一轮按组合走的穷举复验，而不是按条目逐条重看。

Why

实测样本：一批各自单测绿、类型检查绿、也各自做过真机验证的修复，合并之后穷举复验仍查出若干缺陷，其中一部分是本批修复自己引入的回归。 归因分布里没有一条是「实现漏了」，全部是「组合没试过」——所以复验的切分方式必须换轴。 两个形态值得单独盯：一是「打回已上线行为」——改事件通路时，某个订阅方悄悄变成死代码，一条已上线的行为被静默打回， 而它的测试是手动派发事件，永远测不出；二是两条互斥的状态规则可能都「实现正确」，冲突只在组合场景下显形。

Check
会唤起 OS 原生对话框的入口（系统文件选择器、原生确认框）不要点——原生模态接管指针、挡住调试通道，无人值守下会卡死； 这类路径交给单测，并在报告里写明未实测。
13

全量失败集：数目相同不算证据

Rule

大仓库测试套件在全量并发下本身就有抖动，必须与主干逐条 diff，不能比总数。 定性顺序固定三步：① 差异的那几条单独跑，单独跑绿 = 抖动；② 看它在不在本次改动的影响面里（git status 一眼能看出碰没碰、有没有 import 关系）； ③ 再采样一次，两次跑出的若是不同的几条，即为抖动确证。

Why

挂掉一条、修好一条，数目照样对得上。实测样本：纯主干连续两次全量采样，得到的失败集条数不同，且失败的不是同一批用例； 另一次全量出现同一模块的大面积级联失败，而单独跑该文件全绿。 抖动是规模的属性，不是项目的属性——所以既会让人把套件抖动误判成自己引入的回归，也会反过来漏掉真回归。

Check
判成抖动也要写明是哪几条、依据是什么——「看着不相干」不是依据。 取基线不要用 stash：切到主干（或另起基于主干的分支）取；有并行任务在跑时，让某一组在另一个工作树里取。

05 这些东西是怎么被组织起来的 分层法 + 判据与脚本的互相指认

上面每一条单独看都是经验；能不能被别人拿走，取决于它被放在哪一层。所以整包按三层拆 （这里说的三层结构，指的是桌面真机验收与文档生成门禁这两条自研主线； 同包内另有收录的第三方 skill——如 worktree 并行、完成前验证、并行 agent 派发——以及基于 chenglou/pretext 的版式基线件，不在此列）：

  • 通用层——只写判据与硬约束，不出现任何产品名。比如桌面验收侧的通用层把业务耦合收敛到个位数个显式钩子 （应用根目录、启动、主窗口判定、就绪等待、临时 profile 前缀这一类）， 阶段推进、超时、探活、保活、收尾全部不用使用者写；文档生成侧的绑定层则只需填入 DSL、转换器、渲染器探测顺序、素材生成通道等少数几项，判据一律留在通用层。
  • 绑定层——一份填好的真实例子，用来示范「该绑定哪几件事」。换产品只重写这一层。
  • 事故簿——单独存放「这条规则是哪次事故换来的」，故意不进规则包：包只教怎么做对， 事故叙述只在「某条规则看着多余、想删掉」的时候回查。

一个通用层自己的固有失败模式也记在这里：通用层脚本要能住在仓库外—— 阶段推进器曾因为「从规则库目录解析不到依赖」而挂，这不是使用者的问题，是分层本身带来的。
